# Jipsee 기술 명세

Oct 18, 2026 / @윤상준

관련 문서: [Jipsee 기획서 (PRD)](./prd.md)

## 1. 구조

화면과 챗봇은 같은 조회 함수를 사용하고, 응답을 변환하는 부분만 분리함

## 2. 1단계 스택

### 백엔드

| 영역             | 선택                                                                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 언어, 프레임워크 | Java 25 (LTS), Spring Boot 4.1                                                                                                                                         |
| 데이터 접근      | JPA 사용, 대량 적재와 공간 검색은 JdbcTemplate을 사용                                                                                                                  |
| 수집 작업        | Spring Batch 6 + spring-boot-starter-batch-jdbc                                                                                                                        |
| 스케줄 실행      | 스케줄러                                                                                                                                                               |
| 중복 실행 방지   | 수집 날짜를 Job 파라미터로 넘김. 같은 날짜의 Job이 이미 기록돼 있으면 Spring Batch가 두 번째 실행을 거부함 (blue/green 전환 중 컨테이너 2개가 함께 실행되는 경우 대비) |
| 동시 연결        | Spring MVC + 가상 스레드                                                                                                                                               |

### 데이터베이스

| 영역      | 선택                                                        |
| --------- | ----------------------------------------------------------- |
| DB        | MySQL 8.4 LTS                                               |
| 시각      | DATETIME 타입에 UTC로 저장함 (hibernate.jdbc.time_zone=UTC) |
| 검색      | FULLTEXT ngram을 주소, 건물명에 사용함                      |
| 반경 검색 | MBRContains 다음에 ST_Distance_Sphere를 적용함 (long-lat)   |

### 프론트엔드

| 영역       | 선택                                |
| ---------- | ----------------------------------- |
| 프레임워크 | Next.js 16 (App Router), TypeScript |
| UI         | Seed Design                         |
| 구조       | FSD                                 |
| 린트, 포맷 | Biome                               |

### 인프라

| 영역          | 선택                                            |
| ------------- | ----------------------------------------------- |
| 서버          | Oracle A1 (2 OCPU, 12GB, 오사카), Ubuntu        |
| 실행          | Docker Compose                                  |
| 리버스 프록시 | nginx + certbot                                 |
| CI/CD         | GitHub Actions                                  |
| 로그          | 앱 로그 파일                                    |
| 배포          | blue/green (nginx upstream을 전환함)            |
| 요청 제한     | nginx limit_req (화면 API, IP 단위)             |
| 모니터링      | Prometheus, Grafana                             |
| 백업          | mysqldump로 매일 1회 백업하고 최근 7개만 보관함 |

## 4. 데이터 매칭

### 처리 단계

| 단계         | 규칙                                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| 1. 후보 조회 | 지번으로 건축물대장을 조회함. 지번이 없으면 법정동, 건물명, 건축연도로 조회함 (추정)                        |
| 2. 연도 대조 | 건축연도가 필지 안 어느 동의 사용승인 연도와도 다르면 이전 건물 거래로 분리하고, 사용승인일이 없으면 생략함 |
| 3. 결과      | 확정, 추정, 이전 건물, 실패 중 하나로 분류함. 필지까지 맞으면 확정이며 동은 고르지 않음                     |

### 관련 규칙

| 항목        | 규칙                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 법정동 변환 | 시군구 코드와 umdNm을 법정동 사전(앱 리소스 CSV, 연 1회 교체)과 대조함. 읍면 지역은 "읍면 리" 전체로 대조함                           |
| 재매칭      | 표제부 월 적재 직후에, 추정 또는 실패 거래와 표제부가 바뀐 필지의 거래를 대상으로 실행함                                              |
| 품질        | 시군구별로 표본을 수동으로 검수함. 초기 적재 후 시군구별 매칭률을 확인하고, 0%에 가까운 시군구는 시군구 코드가 일치하지 않는지 점검함 |

## 5. 데이터

### 출처

| 데이터              | 출처                                 | 갱신               | 이용 조건                            |
| ------------------- | ------------------------------------ | ------------------ | ------------------------------------ |
| 연립다세대 전월세   | 공공데이터포털 API                   | 매일               | 이용허락범위 미확인                  |
| 연립다세대 매매     | 공공데이터포털 API                   | 매일               | 이용허락범위 미확인                  |
| 건축물대장 (표제부) | 건축HUB 파일                         | 매월               | 이용에 제한이 없음                   |
| 좌표                | 지오코딩 API                         | 표제부를 적재할 때 | 결과 저장을 허용하는 서비스만 사용함 |
| 법령                | 법제처 API (서버 IP를 등록해 호출함) | 개정될 때          | 출처(법제처) 표시 필수               |

### 저장 규칙

| 항목       | 규칙                                                                                                                                                                                                                                |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 원본 보존  | 필드는 원본 값 그대로 저장하되, 금액(콤마가 포함된 문자열, 단위 만원)만 숫자로 변환하고, 화면과 매칭에 쓰지 않는 필드는 저장하지 않음                                                                                               |
| 교체 단위  | 원본에 거래 ID가 없어 행 단위로 수정할 수 없음. API 조회 단위인 시군구와 계약 월(LAWD_CD, DEAL_YMD, 예: 11110, 202509)의 기존 행을 모두 지우고 새로 받은 행을 넣음                                                                  |
| 재수집     | 매일 최근 6개월분을 다시 수집함. 매매 계약이 취소(해제)되면 원래 거래 행에 해제 표시가 나중에 붙으며, 표본에서는 최대 5개월 뒤에 붙었음                                                                                             |
| 수집 순서  | (시군구, 월) 하나씩 API 조회, 교체 조건 확인, 교체를 끝낸 뒤 다음 (시군구, 월)로 넘어감. 동시에 여러 개를 수집하지 않음                                                                                                             |
| 트랜잭션   | (시군구, 월)마다 기존 행 삭제와 새 행 삽입을 한 트랜잭션으로 묶음. 삽입이 실패하면 삭제도 취소됨                                                                                                                                    |
| 교체 조건  | 응답이 불완전하면 기존 행을 지우지 않음. 마지막 페이지까지 받고, resultCode가 000(정상)이고, 받은 건수가 totalCount(API가 알려 준 전체 건수)와 같을 때만 교체함                                                                     |
| 0건 응답   | 기존 행이 있는데 0건이 오면 API 오류로 보고 교체하지 않으며 로그를 남김                                                                                                                                                             |
| 수집 한도  | 오류 22(일일 한도)가 발생하면 다음 날 이어서 수집함                                                                                                                                                                                 |
| 건축물대장 | 최초 적재는 로컬에서 LOAD DATA로 적재한 뒤 덤프를 복원하고, 이후에는 매월 변동분을 반영하며, building_parcel.name은 동이 추가, 삭제되거나 건물명이 바뀐 필지만 다시 계산함                                                          |
| 적재 범위  | 연립 또는 다세대 동이 있는 필지의 모든 동을 적재하고 총괄표제부는 제외함. 주용도와 대장 종류는 대상을 거르는 데에만 사용하고 저장하지 않음                                                                                          |
| 빈 값      | 속성 컬럼은 값이 없으면 NULL, 원본이 0인 수치 컬럼은 0으로 저장함. 식별 컬럼(관리건축물대장PK, 지번주소, 주부속구분)이 비면 해당 행을 건너뛰고 기록을 남김                                                                          |
| 법령 수집  | 매일 1회 법령 4종의 현행 본문을 법령ID로 조회하고(lawService.do target=eflaw), 응답의 법령키와 시행일자를 저장된 값과 비교해 다르면 해당 법령의 조문 전체를 한 트랜잭션으로 교체함. 파싱한 조문이 0건이면 교체하지 않고 로그를 남김 |

### 제약

원본에 동과 호 정보가 없어 건물과 면적 단위로만 비교할 수 있음

## 6. 검색

### 건물 검색

| 항목           | 규칙                                                                              |
| -------------- | --------------------------------------------------------------------------------- |
| 검색 결과 단위 | 필지 단위로 반환함. 한 필지의 여러 동은 building_parcel_id로 묶어 1건으로 보여 줌 |
| 지번 일치      | 검색한 지번 뒤에 숫자가 이어지면 제외함 (12 검색 시 123은 제외, 12-5는 포함)      |
| 검색어 길이    | 2글자 이상 (ngram 색인 단위가 2글자이기 때문)                                     |

## 7. 챗봇

### 처리 순서

1. 사전 검사: 로그인, 이용 제한(user.restricted_at), 봇 차단, 요청 제한을 검사하고, 실패하면 거부 응답을 반환함
2. 주제 제한: 범위 밖 질문이면 안내 문구로 끝내며, 이 단계까지는 LLM 비용이 발생하지 않음
3. LLM 호출: LLM이 도구를 사용해 건물을 조회하고 법령을 검색함
4. 스트리밍: 응답을 스트리밍으로 전달함. nginx 버퍼링은 끄고, 15초마다 heartbeat를 보냄

### 법령 조회

| 항목 | 규칙                                                                                                                    |
| ---- | ----------------------------------------------------------------------------------------------------------------------- |
| 목차 | 저장된 모든 조문의 법령ID, 법령명, 조문 번호, 조문 가지번호, 조문 제목을 챗봇 컨텍스트에 항상 포함함                    |
| 조회 | LLM이 목차에서 (law_id, article_number, branch_number)를 고르면, 법령 검색 도구가 이 키로 law_article에서 원문을 가져옴 |
| 제외 | 법령에는 FULLTEXT 검색과 키워드 검색을 사용하지 않음                                                                    |

### 답변 규칙

| 항목      | 규칙                                                             |
| --------- | ---------------------------------------------------------------- |
| 근거      | 도구 결과(건물 조회, 조문)로만 답변하며, 계산과 추정은 하지 않음 |
| 법령      | 개별 사건에는 전문가 상담을 안내함                               |
| 공시가격  | 공시가격알리미 링크를 안내함                                     |
| 평가 세트 | 통과율이 기준에 미달하면 배포를 중단함                           |
